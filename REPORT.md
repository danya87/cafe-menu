# Звіт до лабораторної роботи №1

## 1. Загальні відомості про роботу

**Лабораторна робота №1**

**Тема:** «Розгортання Java-проєкту та базова обробка даних».

**Індивідуальний варіант:** 5.

**Предметна область:** меню кафе.

**Основна операційна система для локальної розробки:** Windows 11.

У межах роботи створено консольний Java-застосунок, який обробляє набір записів меню кафе, перевіряє вхідні дані, обчислює показники варіанта та формує текстовий звіт.

## 2. Мета роботи

Метою роботи було створення першої працездатної версії Java-програми та одночасне налаштування інфраструктури, необхідної для її відтворюваної збірки й автоматичної перевірки.

У процесі виконання роботи було:

- реалізовано читання даних із UTF-8 файла;
- додано перевірку структури та значень кожного запису;
- реалізовано пропуск некоректних рядків без аварійного завершення програми;
- обчислено показники індивідуального варіанта;
- додано виведення результату в консоль і текстовий файл;
- налаштовано Maven та Maven Wrapper;
- підключено JUnit 5;
- додано статичний аналіз SpotBugs;
- налаштовано створення виконуваного JAR;
- реалізовано GitHub Actions для Windows, Ubuntu та macOS;
- додано параметр командного рядка `--version`.

## 3. Умова індивідуального варіанта

Для варіанта 5 використовується предметна область **«Меню кафе»**.

Один запис описується п'ятьма полями:

```text
name;category;price;weightG;prepMin
```

Призначення полів:

- `name` — назва страви або напою, тип `String`;
- `category` — категорія позиції меню, тип `String`;
- `price` — ціна, тип `double`;
- `weightG` — вага порції у грамах, тип `int`;
- `prepMin` — час приготування у хвилинах, тип `int`.

Для набору коректних записів необхідно визначити чотири показники:

1. кількість коректних записів;
2. середню ціну;
3. найбільшу вагу;
4. найдовший час приготування.

Помилка в одному рядку не повинна припиняти обробку всього файла. Некоректний запис пропускається, а користувач отримує повідомлення з номером рядка та поясненням причини.

## 4. Організація програми

Після реалізації трьох рівнів основні файли проєкту мають таку структуру:

```text
cafe-menu/
├── .github/
│   └── workflows/
│       └── ci.yml
├── .mvn/
│   └── wrapper/
│       └── maven-wrapper.properties
├── data/
│   └── input.csv
├── src/
│   ├── main/
│   │   └── java/
│   │       └── ua/
│   │           └── lpnu/
│   │               └── kzp/
│   │                   └── Main.java
│   └── test/
│       └── java/
│           └── ua/
│               └── lpnu/
│                   └── kzp/
│                       └── MainTest.java
├── .editorconfig
├── .gitattributes
├── .gitignore
├── mvnw
├── mvnw.cmd
├── pom.xml
├── README.md
└── REPORT.md
```

Клас `Main` є точкою входу та виконує загальний сценарій роботи програми:

```text
аргументи командного рядка
        ↓
визначення input/output
        ↓
читання UTF-8 файла
        ↓
перевірка кожного рядка
        ↓
накопичення показників
        ↓
формування звіту
        ↓
консоль + out/report.txt
```

На цьому етапі окремий клас-сутність для позиції меню не створювався. Записи ще обробляються безпосередньо як рядки та поля, оскільки перехід до об'єктної предметної моделі виконується в наступній лабораторній роботі.

`MainTest.java` містить автоматизовані перевірки поведінки програми.

Каталоги `target/` та `out/` внесені до `.gitignore`, оскільки їхній вміст створюється автоматично та може бути відтворений повторним запуском збірки або програми.

## 5. Налаштування збірки та інструментів

Проєкт використовує Maven.

У файлі `pom.xml` задано:

- `groupId` — `ua.lpnu.kzp`;
- `artifactId` — `lab01`;
- версію програми — `1.0.0`;
- цільовий рівень Java — 21;
- кодування вихідного коду та звітів — UTF-8;
- залежність JUnit Jupiter `5.12.2`;
- Maven Compiler Plugin;
- Maven Surefire Plugin;
- SpotBugs Maven Plugin;
- Maven Shade Plugin.

Для відтворюваного запуску Maven у репозиторій додано Maven Wrapper:

```text
mvnw
mvnw.cmd
.mvn/wrapper/
```

На Windows перевірка виконується командою:

```powershell
.\mvnw.cmd clean verify
```

На Unix-подібних системах:

```bash
./mvnw clean verify
```

Maven Wrapper дозволяє використовувати однаковий процес збірки локально та в GitHub Actions.

### Статичний аналіз

SpotBugs виконується під час Maven-фази `verify`.

Таким чином команда:

```powershell
.\mvnw.cmd clean verify
```

виконує не лише компіляцію, а й тести, статичний аналіз та формування пакета програми.

Під час локальної перевірки критичних дефектів SpotBugs не виявлено.

### Виконуваний JAR

Maven Shade Plugin формує виконуваний файл:

```text
target/lab01-1.0.0.jar
```

Головним класом JAR є:

```text
ua.lpnu.kzp.Main
```

Звичайний запуск:

```powershell
java -jar target/lab01-1.0.0.jar
```

Перевірка довідки:

```powershell
java -jar target/lab01-1.0.0.jar --help
```

Перевірка номера версії:

```powershell
java -jar target/lab01-1.0.0.jar --version
```

Результат:

```text
1.0.0
```

### GitHub Actions

Для автоматичної перевірки створено:

```text
.github/workflows/ci.yml
```

Workflow реагує на:

```text
push
pull_request
```

Використовується матриця трьох операційних систем:

- `ubuntu-latest`;
- `windows-latest`;
- `macos-latest`.

На кожному runner встановлюється Temurin JDK 21, після чого запускається Maven Wrapper із командою `verify`.

Поточний CI-запуск завершився успішно для всіх трьох систем:

- Ubuntu — Success;
- Windows — Success;
- macOS — Success.

Після успішного виконання workflow створено три JAR artifacts — окремо для кожної операційної системи.

Для artifact використовується назва, що включає операційну систему та номер запуску workflow.

## 11. Відповіді на контрольні питання

1. **Для чого потрібен `pom.xml`?**  
   Це основний файл Maven-проєкту. У ньому зберігаються координати проєкту, версія, параметри Java, залежності та конфігурація плагінів.

2. **Чим відрізняються `test`, `verify` та `package`?**  
   `test` запускає автоматизовані тести. `package` проходить попередні фази та створює пакет програми. `verify` виконує перевірки, налаштовані для повної валідації проєкту, зокрема SpotBugs.

3. **Навіщо використовувати Maven Wrapper?**  
   Wrapper дає можливість запускати Maven через файли, що зберігаються разом із проєктом, і не залежати від різних локальних конфігурацій Maven.

4. **Яке призначення методу `main`?**  
   `main` є початковою точкою виконання консольного Java-застосунку та отримує аргументи командного рядка.

5. **Чим примітивний тип відрізняється від `String`?**  
   Примітивні типи безпосередньо представляють прості значення, наприклад `int` або `double`. `String` є класом, тому змінна цього типу працює з об'єктом.

6. **Чому середнє значення слід обчислювати як `double`?**  
   Результат ділення може містити дробову частину. Використання лише цілих типів призвело б до її втрати.

7. **Що станеться для `Integer.parseInt("abc")`?**  
   Java не зможе перетворити такий текст у ціле число й буде створено `NumberFormatException`.

8. **Чому помилкові рядки не можна просто ігнорувати?**  
   Повідомлення про номер та причину помилки дозволяє користувачеві зрозуміти, які саме дані не були враховані.

9. **Для чого в `split(";", -1)` використовується `-1`?**  
   Такий виклик не відкидає порожні поля в кінці рядка. Тому можна правильно виявити ситуацію, коли останнє значення відсутнє.

10. **Чому використовується `Path.of`?**  
    `Path` надає стандартний Java-механізм роботи зі шляхами та не прив'язує програму до синтаксису конкретної операційної системи.

11. **Навіщо явно вказувати UTF-8?**  
    Це робить читання й запис тексту незалежним від системного кодування та забезпечує правильну роботу українських символів.

12. **Чим `%n` відрізняється від `\n`?**  
    `%n` використовує правильний для поточної платформи роздільник рядків, тому краще підходить для кросплатформного форматованого виведення.

13. **Які дані перевіряються у варіанті 5?**  
    Перевіряється наявність п'яти полів, непорожні `name` і `category`, числовий формат `price`, `weightG` та `prepMin`, а також відсутність недопустимих від'ємних значень.

14. **Як перевірити правильність обчислення середнього?**  
    Потрібно взяти кілька значень із наперед відомою сумою та середнім і порівняти очікуваний результат з результатом програми.

15. **Навіщо потрібен статичний аналізатор?**  
    Він аналізує код або байт-код і допомагає знайти потенційні проблеми, які можуть не проявитися під час звичайних тестів.

16. **Для чого використовується GitHub Actions?**  
    GitHub Actions автоматично запускає однакову процедуру збірки й тестування після змін у репозиторії та дозволяє перевірити програму на різних ОС.

17. **Яку інформацію слід додати до Issue про дефект?**  
    Потрібно описати проблему, спосіб її відтворення, очікуваний результат і фактичну поведінку.

18. **Що зазначається у розділі академічної доброчесності?**  
    Потрібно вказати використані ШІ-інструменти, їхню роль у роботі, приклади запитів, використані рекомендації та виправлені під час роботи проблеми.

## 4. Клас-сутність MenuItem

Клас `MenuItem` описує одну позицію меню та містить поля:

```text
name
category
price
weightG
prepMin
```

Усі поля оголошено як `private final`, а сам клас — `final`. Setter-и відсутні.

Перевірка стану виконується в конструкторі.

Основні інваріанти:

- `name` не може бути `null` або порожнім;
- `category` не може бути `null` або порожньою;
- `price` повинна бути скінченним числом;
- `price >= 0`;
- `weightG >= 0`;
- `prepMin >= 0`.

Якщо хоча б одна умова порушується, об'єкт не створюється.

Для читання стану використовуються методи:

```text
getName()
getCategory()
getPrice()
getWeightG()
getPrepMin()
```

Метод `toString()` формує текстове представлення позиції меню з використанням `Locale.ROOT`.

Для допоміжного отримання ціни та ваги використовується:

```java
getPriceWeight()
```

### Незмінність

`MenuItem` є повністю незмінним об'єктом:

- клас оголошений `final`;
- поля мають `private final`;
- setter-и відсутні;
- після успішного створення стан об'єкта не змінюється.

Незмінні об'єкти зручні під час передавання між потоками, оскільки інший код не може несподівано змінити їхній стан. Це зменшує ризик помилок, пов'язаних зі спільним доступом до змінних даних.

### Builder

Для поетапного створення `MenuItem` реалізовано:

```java
MenuItem.Builder
```

Builder дозволяє задати:

```text
name
category
price
weightG
prepMin
```

Метод:

```java
build()
```

створює об'єкт через основний конструктор `MenuItem`.

Таким чином Builder не дублює і не обходить правила валідації.

Для перетворення одного CSV-рядка в об'єкт використовується:

Очікуваний формат:


Для допоміжного незмінного значення створено:

```java
PriceWeight
```


Під час створення перевіряється:

- ціна не є від'ємною;

Record автоматично надає методи доступу до компонентів, `equals()`, `hashCode()` і `toString()`.

## 11. Відповіді на контрольні питання

1. **Яку проблему розв'язує клас-сутність порівняно з рядком і паралельними змінними?**  
   Клас-сутність об'єднує пов'язані дані та правила їх перевірки в одному місці. Це спрощує роботу з одним записом і зменшує ризик помилок.

2. **Що означають `private` і `final` у полях класу?**  
   `private` забороняє прямий доступ до поля з інших класів, а `final` не дозволяє переприсвоїти поле після створення об'єкта.

3. **Що таке інкапсуляція і яку проблему вона запобігає?**  
   Інкапсуляція приховує внутрішній стан об'єкта та дозволяє працювати з ним лише через визначені методи. Це захищає дані від неконтрольованої зміни.

4. **Чому перевірку інваріантів розміщують у конструкторі?**  
   Щоб об'єкт неможливо було створити у некоректному стані.

5. **Чим `Objects.requireNonNull` відрізняється від `isBlank`?**  
   `requireNonNull` перевіряє, що посилання не є `null`, а `isBlank` перевіряє, чи рядок не є порожнім або складеним лише з пробілів.

6. **Чому відсутність setter-ів може допомогти зберегти коректний стан?**  
   Після створення об'єкта його перевірені значення не можна довільно змінити.

7. **Які методи й властивості автоматично отримує record?**  
   Record отримує конструктор, методи доступу до компонентів, `equals()`, `hashCode()` і `toString()`.

8. **Чим record відрізняється від звичайного класу-сутності?**  
   Record призначений для компактного представлення даних і потребує менше службового коду.

9. **Чому record не гарантує глибоку незмінність змінного списку?**  
   Якщо компонент record містить змінний об'єкт, наприклад `List`, його вміст усе одно можна змінювати.

10. **Для чого потрібен статичний фабричний метод `fromCsv`?**  
    Він перетворює CSV-рядок у готовий об'єкт `MenuItem` і відокремлює розбір рядка від решти логіки.

11. **Де потрібно перехоплювати помилку розбору одного рядка?**  
    У циклі читання файла в `Main`, щоб одна помилка не припиняла обробку всього файла.

12. **Чому неправильний запис не можна додавати до списку до завершення перевірки?**  
    Некоректні значення можуть потрапити до статистики та змінити результат.

13. **Яке призначення `toString()` і чому він не замінює формат CSV?**  
    `toString()` створює зрозуміле текстове представлення об'єкта. CSV є окремим форматом вхідних даних.

14. **Навіщо використовувати `Locale.ROOT` у `toString()` і звіті?**  
    Щоб формат дробових чисел не залежав від локальних налаштувань операційної системи.

15. **Що означає схема тесту AAA?**  
    Arrange — підготовка даних, Act — виконання дії, Assert — перевірка результату.

16. **Які негативні випадки потрібно перевірити для конструктора?**  
    `null`, порожні рядки, від'ємні та інші значення, які порушують інваріанти класу.

17. **Як довести, що рефакторинг не змінив зовнішню поведінку попередньої роботи?**

## 4. Базовий тип MenuItem

`MenuItem` є спільним базовим типом для всіх позицій меню.

Ієрархія:

```text
MenuItem
├── Dish
├── Drink
└── Dessert
```

У базовому типі зберігаються спільні поля:

```text
name
category
price
weightG
prepMin
kind
```

Усі поля оголошено як `private final`, setter-и відсутні.

Основні інваріанти:

- `name` не може бути `null` або порожнім;
- `category` не може бути `null` або порожньою;
- `price` повинна бути скінченним числом;
- `price >= 0`;
- `weightG >= 0`;
- `prepMin >= 0`;
- `kind` не може бути `null`.

Спільні правила перевірки винесені до `MenuItem` і не дублюються у підтипах.

Для читання стану використовуються методи:

```text
getName()
getCategory()
getPrice()
getWeightG()
getPrepMin()
getKind()
```

Поліморфна операція оголошена у базовому типі:

```java
preparationCost()
```

Вона має різну реалізацію в кожному підтипі.

### Вибір абстрактного класу

Для `MenuItem` використано абстрактний клас, а не інтерфейс, оскільки всі позиції меню мають спільний стан: назву, категорію, ціну, вагу, час приготування та тип.

Абстрактний клас дозволяє зберігати цей стан, реалізувати спільні методи й централізувати валідацію.

### Вибір спадкування

Для моделі використано спадкування, оскільки `Dish`, `Drink` і `Dessert` є різновидами `MenuItem`.

Це відповідає відношенню `is-a`:

- `Dish` є `MenuItem`;
- `Drink` є `MenuItem`;
- `Dessert` є `MenuItem`.

Композиція була б доречною, якби один об'єкт лише містив або використовував інший об'єкт. У цій моделі підтипи є спеціалізаціями одного базового поняття, тому спадкування є природнішим рішенням.

## 5. Підтипи

Реалізовано три конкретні підтипи:

```text
Dish
Drink
Dessert
```

Класи підтипів оголошені як `final`.

### Dish

`Dish` представляє страву.

Поліморфна вартість приготування:

```text

```

### Drink

`Drink` представляє напій.

Поліморфна вартість приготування:

```text
price * 0.15
```

### Dessert

`Dessert` представляє десерт.

Поліморфна вартість приготування:

```text
price * 0.25
```

У всіх підтипах метод `preparationCost()` перевизначено через `@Override`.

Завдяки цьому код, який працює з `MenuItem`, не повинен перевіряти конкретний клас об'єкта.

## 7. equals і hashCode

У `MenuItem` реалізовано узгоджені методи:

```java
equals()
hashCode()
```

Критерій логічної рівності:

- об'єкти повинні належати до одного конкретного підтипу;
- `name` повинно збігатися;
- `category` повинно збігатися;
- `price` повинна збігатися;
- `weightG` повинна збігатися;
- `prepMin` повинно збігатися;
- `kind` повинен збігатися.

Для перевірки конкретного підтипу використовується `getClass()`.

Це означає, що об'єкти різних підтипів не стають рівними лише через однакові значення полів.

Контракт `equals()` і `hashCode()` перевірено автоматизованими тестами.

Для додаткової перевірки використовується `HashSet`.

Після додавання двох логічно рівних об'єктів одного підтипу розмір множини залишається рівним `1`.

Це підтверджує узгодженість `equals()` і `hashCode()`.

## 8. Поліморфізм

Різнорідні об'єкти зберігаються у колекції спільного типу:

```java
List<MenuItem>
```

У колекції одночасно можуть знаходитися:

```text
Dish
Drink
Dessert
```

Виклик:

```java
item.preparationCost()
```

автоматично виконує реалізацію конкретного підтипу.

Основний код не використовує перевірки виду:

```java
if (item instanceof Dish) ...
if (item instanceof Drink) ...
if (item instanceof Dessert) ...
```

для обчислення `preparationCost()`.

Таким чином вибір конкретної реалізації виконується механізмом поліморфізму Java.

### Sealed-ієрархія

У межах завдання із зірочкою `MenuItem` оголошено як `sealed`.

Дозволені підтипи визначені через `permits`:

```text
Dish
Drink
Dessert
```

Усі безпосередні підтипи оголошені як `final`.

Для окремої допоміжної операції реалізовано вичерпний pattern-matching `switch`.

Він має гілки для:

```text
Dish
Drink
Dessert
```

Гілка `default` не потрібна, оскільки компілятор знає повний список дозволених підтипів sealed-ієрархії.

Якщо до `permits` додати новий підтип і не додати відповідну гілку до `switch`, компілятор повідомить про невичерпний `switch`.

Pattern-matching `switch` не використовується для `preparationCost()`, оскільки це дублювало б уже реалізовану поліморфну поведінку.


### Порівняння реалізацій

У Lab 2 вся позиція меню представлялася одним класом `MenuItem`.

Перевагою такого підходу була простота: усі записи мали однаковий тип.

Недоліком було те, що додавання різної поведінки для окремих видів позицій меню вимагало б централізованих умов `if` або `switch`.

У Lab 3 спільний стан залишився у `MenuItem`, а відмінна поведінка перенесена до `Dish`, `Drink` і `Dessert`.

Поліморфна реалізація має такі переваги:

- основний код працює з одним типом `MenuItem`;
- логіка конкретного підтипу знаходиться в самому підтипі;
- для `preparationCost()` не потрібні перевірки класу;
- нову поведінку простіше локалізувати;
- модель точніше відображає предметну область.

Недоліком є більша кількість класів та складніша структура порівняно з Lab 2.

Основна перевага Lab 3 полягає не у швидкості, а в кращому розділенні відповідальності та можливості розширення моделі.

Таким чином перехід до поліморфної моделі змінив внутрішню архітектуру програми, але не змінив її зовнішню поведінку.

## 14. Відповіді на контрольні питання

1. **Яку спільну проблему розв'язує базовий тип у предметній області?**

   Базовий тип зберігає спільний стан і спільний контракт для різних сутностей. У цій роботі `MenuItem` дозволяє працювати зі стравами, напоями та десертами через один тип.

2. **Чим відрізняються `extends` і `implements`?**

   `extends` використовується для успадкування класу або розширення інтерфейсу, а `implements` — коли клас реалізує контракт інтерфейсу.

3. **Навіщо базовий клас може бути `abstract`?**

   Щоб заборонити створення занадто загального об'єкта та визначити спільний стан і методи, які конкретні підтипи повинні реалізувати.

4. **Яку роль виконує виклик `super(...)` у конструкторі підтипу?**

   Він викликає конструктор базового класу та передає йому значення спільних полів.

5. **Що перевіряє анотація `@Override`?**

   Вона підтверджує, що метод дійсно перевизначає метод базового класу або реалізує метод інтерфейсу.

6. **Що таке поліморфізм і як він усуває розгалуження за типом?**

   Поліморфізм дозволяє викликати один спільний метод через базовий тип, а конкретна реалізація вибирається відповідно до реального класу об'єкта.

7. **Коли краще використати інтерфейс, а коли абстрактний клас?**

   Інтерфейс зручний для спільного контракту без спільного стану. Абстрактний клас доречний, коли підтипи мають спільні поля та спільну реалізацію.

8. **Що означає відношення «є різновидом» і чим воно відрізняється від композиції?**

   `is-a` означає, що підтип є спеціалізацією базового типу. Композиція `has-a` означає, що один об'єкт містить або використовує інший.

9. **Для чого використовують enum із полями та методами?**

   Enum описує фіксований набір допустимих значень і може додатково зберігати дані та поведінку для кожної константи.

10. **Чому значення enum можна порівнювати через `==`?**

    Кожна константа enum створюється JVM один раз, тому порівняння через `==` є коректним.

11. **Які правила має виконувати пара `equals/hashCode`?**

    Якщо два об'єкти рівні за `equals()`, їх `hashCode()` повинен бути однаковим.

12. **Чому змінне поле небезпечне для об'єкта, який є ключем `HashMap`?**

    Якщо поле, що бере участь у `hashCode()`, змінити після додавання об'єкта до `HashMap`, колекція може більше не знайти цей ключ.

13. **Чому два об'єкти різних підтипів можуть бути нерівними за однакової назви?**

    Тому що конкретний тип може бути частиною предметної ідентичності об'єкта.

14. **Як поліморфна колекція обробляє об'єкти різних підтипів?**

    `List<MenuItem>` зберігає посилання базового типу, а JVM автоматично викликає перевизначену реалізацію фактичного підтипу.

15. **Які тести доводять, що підтипи мають різну поведінку?**

    Тести створюють `Dish`, `Drink` і `Dessert` та перевіряють різні результати `preparationCost()`.

16. **Які тести доводять коректність рівності в `HashSet`?**

    До `HashSet` додаються два логічно рівні об'єкти, після чого перевіряється, що розмір множини дорівнює `1`.

17. **Що контролює `sealed` і навіщо потрібен `permits`?**

    `sealed` обмежує перелік класів, які можуть успадковувати базовий тип, а `permits` задає дозволені підтипи.

18. **Чому `switch` за підтипами не повинен дублювати поліморфні методи?**

    Дублювання створило б дві точки підтримки однієї логіки. У цій роботі `preparationCost()` реалізовано через поліморфізм, а `switch` використовується лише для допоміжної операції.
